## 4. Security findings

### 4.1 Open redirect (CRITICAL — fixed and verified)

The login page accepted `?next=` and validated it with:

```ts
requested.startsWith('/') && !requested.startsWith('//')
```

That check is defeated by the browser's own URL normalisation, because `\` is treated as `/`:

| Payload | Old guard | Resolves to |
| --- | --- | --- |
| `/\evil.com` | **passes** | `https://evil.com/` |
| `/\t/evil.com` | **passes** | `https://evil.com/` |
| `/\evil.com/..` | **passes** | `https://evil.com/` |
| `//evil.com` | blocked | — |

A link `.../login?next=/\evil.com` sent to a student would, immediately after a *successful* login on the real domain, land them on an attacker's lookalike page. For a product used by minors that is a phishing vector, not a cosmetic bug.

**Fix.** Stop pattern-matching strings; let the URL parser normalise exactly as the browser will, then require the result to be same-origin (`src/lib/safeRedirect.ts`). Auth routes are also excluded to prevent loops. **30 unit tests** cover 13 attack payloads, 6 legitimate paths, and login-loop prevention; a **browser regression check** signs in for real and asserts the URL never leaves the origin.

**Verified:** 5 attack payloads blocked end-to-end in Chromium; `/app/quizzes` still honoured.

### 4.2 Unsafe AI output (hardened)

`react-markdown` already strips `javascript:`, `data:` and `vbscript:` URLs — verified empirically against 8 payloads. It passes `javascript&colon;alert(1)` through unchanged, which is not exploitable when React sets attributes via the DOM, but relying on that is fragile. Added an explicit allowlist (`src/lib/markdownUrl.ts`, **19 tests**). KaTeX `trust` is **off**, so the KaTeX advisory is not reachable; the model cannot emit `\href`.

### 4.3 Dependency posture

| Stage | Critical | High | Moderate | Low | Total |
| --- | --- | --- | --- | --- | --- |
| Baseline | 2 | 17 | 6 | 4 | 29 |
| Final | **0** | 16 | 3 | 4 | **23** |

Remaining production-runtime findings, all assessed:
- **firebase (high)** — via `@grpc/grpc-js`, Node-only. The browser build uses WebChannel. Firebase is **not configured**, so this code never executes.
- **katex / rehype-katex / remark-math (low)** — prototype pollution that bypasses `trust`; trust is off.
- Remaining 16 high are build/test tooling (`@vercel/node`, `tailwindcss` → braces/micromatch, `ts-morph`, `undici`, `@fastify/busboy`). Not shipped to users. `npm audit --audit-level=critical` gates CI so a *critical* advisory blocks a release.

## 6. Accessibility and UI/UX

axe-core was run across **20 combinations** — 12 public pages in light theme, 5 in dark, 2 at 360 px, plus auth screens — tagged WCAG 2.1 A/AA.

**Baseline: 5 pages with serious violations.** All were contrast:

| Element | Ratio | Requirement |
| --- | --- | --- |
| Warning/demo badge | 3.08:1 | 4.5:1 |
| "Exam relevant" badge | 3.25:1 | 4.5:1 |
| Chat bubble, dark mode | 2.13:1 | 4.5:1 |
| Alert bodies | ~4.3:1 | 4.5:1 |

**After:** 0 critical or serious violations in **both themes and at mobile width**, locally and on production. The fixes were token-level rather than per-component: a theme-aware `--accent-text` (dark theme needs lighter, not darker), `--success-contrast`, and removing `opacity-90` from alert bodies. Four further components using the same failing mix were fixed proactively even though axe did not reach them.

**Not covered:** screen-reader testing, reduced-motion behaviour, and 200% browser zoom. These need a human with a screen reader.

## 14. Organic growth — next 30 days

The product already has honest content and correct technical foundations. What it lacks is **evidence that students learn with it**, and that is what should be built next — not more pages.

**Weeks 1–2 — prove the loop works (no new content)**
Recruit 10–15 students from one school or coaching centre. Watch five sessions in person. Instrument nothing new; use what exists. Success = you can name the exact point where students get stuck.

**Weeks 2–3 — fix what they hit**
Almost certainly: answer accuracy in Nepali (§ the arithmetic errors already found and partly fixed) and quiz difficulty calibration. Any new practice-question generator must be spot-checked by a human before publishing.

**Weeks 3–4 — depth on pages that already rank-or-should**
Only five pages carry real search intent today: `/see-preparation`, `/courses/see-mathematics-core`, `/grades/10`, `/subjects`, `/ai-tutor`. Add worked examples with real marking-style explanations to those — one excellent page beats ten thin ones. Every new guide needs a named author, a source, and a licence, which the admin panel already enforces.

**Do not** mass-generate grade × subject pages. The 12 grade hubs are already near the thin-content line, and Google's 2024–2026 updates penalise exactly that pattern.

**Measurement.** No analytics exists. Before adding any, decide the two numbers that matter (likely: students completing ≥1 quiz per week, and 7-day return rate), and add privacy-respecting analytics only with consent handling and a privacy-policy update in the same change. **No traffic, ranking or revenue figure in this document is a prediction.**

## 15. Launch-readiness decision

### READY WITH LIMITATIONS

**Ready:** security posture (no exploitable findings after the redirect fix), correctness of the core study loop, performance within all three Core Web Vitals targets, accessibility at WCAG 2.1 AA for automated checks, SEO/GEO surface complete and verified, and a release gate that blocks regressions.

**Limitations — do not ship to real students until these are closed:**

1. **Firebase is not configured.** Accounts and the admin library run in browser-only demo mode, clearly labelled. Firestore rules are written but **never deployed or tested**. Account isolation, password reset and cross-device sync are therefore unproven.
2. **The CI and monitoring workflows have never run.** They activate when the repo is pushed to GitHub.
3. **Accessibility was verified automatically, not by a person using a screen reader.**
4. **AI accuracy is improved but not solved.** A prompt-level self-check fixed the two arithmetic errors found in a Nepali answer; the model remains non-deterministic. Any student-facing use should keep the AI-generated labelling and a "report this answer" path (which exists).

**Recommended next action, in order:** push to GitHub (workflows start) → create the Firebase project and deploy rules (closes the largest unknown) → run a 10-student pilot.
